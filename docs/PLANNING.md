## 1. 왜 만들었나

### 문제

> 나중에 볼 링크는 카톡 '나에게 보내기'에, 가고 싶은 식당은 스크린샷으로, 떠오른 생각은 메모 앱에.
> **저장은 했는데 어디에 뒀는지 몰라서 결국 다시 찾지 못하는** 정보들.

정보를 모으는 도구는 이미 많습니다. 그런데도 저장한 것을 다시 못 찾는 이유는 두 가지입니다.

1. **저장하는 순간에 비용이 든다** — 어느 앱에, 어느 폴더에, 무슨 제목으로 넣을지 정해야 합니다. 그 판단이 귀찮아서 결국 "일단 여기"에 던지고, 그렇게 흩어집니다
2. **찾을 때 이름을 알아야 한다** — 폴더와 검색은 사용자가 그때 붙인 이름을 기억하고 있다는 전제 위에 있습니다. 몇 주 지나면 그 전제가 깨집니다

### 가설

**저장할 때는 아무 결정도 요구하지 않고, 정리는 나중에 AI가 하고, 찾을 때는 이름이 아니라
"의미"로 접근하게 하면** 사람들이 저장한 것을 실제로 다시 쓸 것이다.

### 이름의 뜻

**우주인** = **우**리 **주**변의 **인**포메이션. 동시에 저장물이 별이 되어 성좌를 이루는
"나만의 우주"라는 은유이기도 합니다. 이 은유는 이름에만 머물지 않고 제품의 메인 뷰
(3D 성좌)로 구현되어 있습니다.

## 2. 무엇을 만들었나

### 한 문장

흩어진 링크·사진·메모를 어디서든 1초에 던져 넣으면, AI가 제목·요약·카테고리를 붙여 정리하고,
**의미가 가까운 것끼리 모인 3D 우주**로 되찾게 해주는 올인원 AI 스크랩북.

### 세 가지 핵심 가치

| 가치 | 무엇을 뜻하는가 | 제품에서 |
| --- | --- | --- |
| **저장은 1초** | 저장 순간에 어떤 결정도 요구하지 않는다 | 형식(링크/사진/메모)만 던지면 끝. 폴더·태그·제목 입력 없음. 서버는 AI 처리를 기다리지 않고 즉시 응답 |
| **정리는 AI가** | 분류·요약은 사용자의 일이 아니다 | 제목·요약 생성, 카테고리 자동 분류, 사진 OCR·설명, 위치 추출이 백그라운드에서 진행 |
| **찾을 땐 검색 한 번** | 이름을 기억하지 못해도 찾을 수 있다 | 자연어 문장 검색, 키워드가 안 걸리면 의미(임베딩) 검색, 그리고 눈으로 훑는 3D 성좌 |

### 경쟁 제품과의 차이

| | 메모 앱 (노션·에버노트) | 북마크 도구 (Raindrop 등) | **우주인** |
| --- | --- | --- | --- |
| 저장 시 분류 | 사용자가 직접 | 사용자가 직접 | **AI가 자동** |
| 다루는 형식 | 주로 텍스트 | 주로 링크 | **링크 · 사진 · 메모 통합** |
| 되찾는 방법 | 폴더 · 키워드 | 태그 · 키워드 | 키워드 + **자연어** + **의미** + **공간(3D·지도)** |
| 저장 통로 | 앱 · 확장 | 확장 | 웹 · 확장 · 모바일 공유 · **메신저** · **워치** |

핵심 차별점은 **"저장 통로의 넓이 × 되찾는 방법의 다양성"** 입니다. 어느 하나만으로는
기존 도구와 구분되지 않지만, 던져 넣는 비용이 0에 가까워지면 저장량이 늘고, 저장량이 늘면
목록형 탐색이 무너집니다. 그때 공간형 탐색(성좌·지도)과 의미 검색이 필요해집니다.

## 3. 타깃과 사용 시나루오

### 주 타깃

**정보를 많이 접하지만 정리할 시간이 없는 사람** — 대학생·취준생·주니어 직장인.

- 하루에 링크·스크린샷을 수십 개 접하고, "나중에 보자"며 저장은 하지만 정리는 안 한다
- 이미 여러 도구에 흩어져 있고, 새 도구를 배우는 데 시간을 쓰고 싶지 않다

### 시나리오

**① 맛집 (개인)**
> 인스타에서 본 식당 링크를 공유 시트로 우주인에 던진다. 잠시 뒤 알림이 온다 — 제목·요약이
> 붙고 `음식·맛집`으로 분류돼 있다. 몇 주 후 그 동네에 갔을 때 **지도 뷰**를 열면 근처에
> 저장해 둔 핀이 보인다. 이름은 기억나지 않았다.

**② 학습 (개인)**
> 공부하다 만난 아티클을 크롬 확장 버튼으로 저장한다. 나중에 `"저번에 본 그 인덱스 설명글"`
> 이라고 AI 검색에 넣으면, 제목에 "인덱스"가 없어도 의미가 가까운 글이 나온다.

**③ 팀 (협업)**
> 팀 Discord 채널을 워크스페이스에 매핑해 두면, 누가 채널에 슬래시 명령으로 링크를 던져도
> 팀 워크스페이스에 쌓인다. 다른 멤버 화면에는 **새로고침 없이** 실시간으로 나타난다.

**④ 손목 (Wear OS)**
> 걷다가 괜찮은 카페를 봤다. 폰을 꺼내지 않고 워치 버튼으로 **지금 있는 장소**를 저장한다.
> 주변 장소 후보에서 이름을 고르면 끝.

## 4. 기능 범위

### 저장 통로 (5개)

| 통로 | 무엇을 저장하나 |
| --- | --- |
| 웹앱 | 링크 · 사진 · 메모 |
| Chrome 확장 | 보고 있는 페이지 (툴바 버튼 / 우클릭 메뉴) |
| 모바일 공유 시트 | PWA Share Target — 링크 · 텍스트 · 이미지 |
| Discord · Mattermost | 채널에서 슬래시 명령 |
| Wear OS | 현재 위치 · 음성 메모 · 듣고 있는 노래 |

### 뷰 (3개)

| 뷰 | 목적 |
| --- | --- |
| **성좌** | 의미가 가까운 것끼리 모인 3D 공간. 메인 뷰 |
| **라이브러리** | 카테고리 칩으로 걸러 보는 카드 목록 |
| **지도** | 좌표가 있는 저장물의 지리적 배치 |

### 그 외

- 키워드 검색 / AI 자연어 검색 / 의미 검색 폴백
- 카테고리 관리 (기본 11종 + 사용자 추가), 즐겨찾기, 휴지통(복원·영구삭제)
- 개인 스페이스 + 공유 워크스페이스(초대·권한·추방·활동 피드)
- 웹 푸시 알림 + SSE 실시간 반영
- 마이페이지 — 프로필, 통계, AI 사용량, 연결된 기기, 메신저 연동

> 요구사항 단위의 상세 목록과 구현 상태는 [요구사항 명세서](REQUIREMENTS.md)에 있습니다.

## 5. 화면 구조

```
비로그인
├── /                     랜딩 (서비스 소개)
├── /login  /signup       로그인 · 이메일 가입
├── /oauth/callback       구글 로그인 콜백
├── /oauth/onboarding     구글 신규 가입 온보딩 (닉네임 · 약관 동의)
├── /invite/:code         초대 미리보기 (참여는 로그인 후)
└── /privacy              개인정보처리방침

로그인 후
├── /home                 로그인 직후 도착지 → 개인 스페이스 성좌
├── /my                   마이페이지
├── /share-target         OS 공유 시트 진입점 (사이드바 없는 단독 화면)
└── /workspace/:id
    ├── universe          성좌 (기본)
    ├── library           라이브러리
    ├── map               지도
    └── trash             휴지통
```

**설계 의도**

- 워크스페이스 하위 세 뷰는 **상단 헤더(제목·뷰바)를 공유**합니다 — 같은 데이터를 다르게 보는 것이므로 화면 전환이 아니라 시선 전환으로 느껴져야 합니다
- 워크스페이스 레이아웃은 화면을 그리지 않고 **SSE 구독만** 합니다 — 휴지통까지 한 연결로 덮습니다
- `/share-target`과 `/invite/:code`는 사이드바 없는 단독 화면입니다 — 외부에서 곧바로 들어오는 진입점이라 앱 셸을 먼저 보여줄 이유가 없습니다
- 3D·지도는 라이브러리가 무거워 **라우트 단위로 lazy 분할**했습니다. 랜딩·로그인 첫 로딩에 three/maplibre가 딸려오지 않습니다

## 6. 핵심 사용자 흐름

### 저장 → 정리 → 알림

```
사용자가 던진다
    │
    ▼
저장 API ──── 즉시 201 (status: PROCESSING) ────▶ 사용자는 하던 일을 계속한다
    │
    └─▶ Redis Streams 큐
             │
             ▼
        백그라운드 워커 (컨슈머 3)
             ├─ 트랙 A: 미리보기 (oEmbed/OG) ─── 거의 항상 성공
             └─ 트랙 B: 콘텐츠 확보 ──────────── 실패 가능
                      │
                      ▼
             AI: 제목·요약 → 카테고리 분류 → 임베딩 → 3D 좌표 재계산
                      │
                      ▼
             상태 확정: DONE / PARTIAL / FAILED
                      │
                      ├─▶ 웹 푸시 (DONE · PARTIAL만)
                      └─▶ SSE `item` 이벤트 → 열려 있는 화면 갱신
```

**이 흐름에서 타협하지 않은 것**

1. **저장 경로에 동기 AI 호출을 넣지 않는다** — "저장은 1초"가 무너지는 순간 이 제품의 전제가 무너집니다
2. **트랙 A와 B는 서로 영향을 주지 않는다** — 크롤링이 막혀도 미리보기 카드는 남습니다(`PARTIAL`). 저장한 것이 통째로 사라지는 경험을 만들지 않습니다
3. **알림을 못 받는 사용자를 위한 폴백이 있다** — 알림 거부 시 상태 조회 API로 완료를 확인합니다

### 되찾기

```
                  ┌─ 이름이 기억난다 ──────▶ 키워드 검색
                  │                            └─ 0건이면 의미 검색으로 폴백
"저장한 거 찾기" ─┼─ 문장으로만 떠오른다 ──▶ AI 검색 ("그 파스타집 어디였지?")
                  │
                  ├─ 뭘 찾는지 모르겠다 ───▶ 성좌 (비슷한 것끼리 모여 있다)
                  └─ 장소가 기억난다 ──────▶ 지도
```

## 7. 설계 결정

3주라는 일정 안에서 **되돌리기 비싼 결정**만 미리 정하고, 나머지는 구현하며 정했습니다.

| # | 결정 | 이유 |
| --- | --- | --- |
| 1 | 저장은 즉시 응답 + 큐 기반 비동기 가공 | 제품의 핵심 약속. 동기 처리로 시작하면 나중에 뜯는 비용이 크다 |
| 2 | 검색은 PostgreSQL로 (Elasticsearch 배제) | 부분 인덱스 + pgvector로 필요한 수준을 만족. 3주에 검색 인프라 운영까지는 무리 |
| 3 | 지도는 OpenFreeMap + MapLibre | 타일 호스팅 무료·API 키 불필요. 카카오는 **주소↔좌표 REST**만 사용 |
| 4 | AI는 사이드카(FastAPI)로 분리 | 모델·프롬프트 교체가 백엔드 배포와 독립. 임베딩·UMAP처럼 파이썬 생태계가 필요한 작업이 섞여 있다 |
| 5 | 외부 의존성은 전부 **없어도 뜨게** | 팀원 6인이 각자 로컬에서 돌려야 한다. 키 하나 없다고 앱이 안 뜨면 개발이 막힌다 |
| 6 | 웹앱은 Vite SPA + PWA (Next.js 배제) | 설치형 경험(공유 시트·푸시)이 SSR보다 중요했다 |
| 7 | 스키마는 Flyway가 소유 (`ddl-auto: validate`) | `update`가 조용히 스키마를 바꾸고 실패해도 WARN만 남겨 사고를 만든 적이 있다 |
| 8 | 배포 대상은 브랜치가 정한다 | `develop`→dev, `main`→prod. 사람이 고르면 실수한다 |

배제한 기술과 그 이유는 [요구사항 명세서 — 범위에서 제외한 것](REQUIREMENTS.md#범위에서-제외한-것)에 정리돼 있습니다.
